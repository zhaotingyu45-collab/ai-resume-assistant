# AI 求职经历资产管理助手

个人项目，2026.11，可本地运行的离线 Demo。

求职的时候同一段经历投不同岗位要改好几版，改着改着容易把「参与」写成「主导」。想贴 JD 又怕夸大，这是这个项目要解决的矛盾。做法是把经历先攒成自己的库，再按岗位出版本——事实锁死，表达放开。

浏览器打开 `index.html` 就能用，`core.js` 需和它放在同一目录。右上角设置里填 DeepSeek API Key，只存本机浏览器。评测在单独的 `eval.html`，不挂进产品界面——F1、注入缺陷这些是开发时看的，用户不需要看见。

## 怎么做的

六个固定节点：经历结构化 → JD 解析 → 匹配 → 缺口识别 → 简历生成 → 事实校验。没用多 Agent，每一步的输入输出都能单独查看，出问题能定位到具体节点。

几个关键取舍：

**AI 只提候选，人来确定。** 经历抽成标签后默认「待确认」，每条带着原文证据，人点了确认才算数。没确认的不进后续匹配和生成。这样幻觉传不下去，出错也能归因。

**事实和表达分开管。** 数字、项目名、职责强度词、事实点必须能映射回原文（输出里带 `fact_map`）；但背景、职责、行动允许按 JD 的措辞改写。早先做过一版全程强校验的，结果经历填不全就被卡住，放弃了。

**匹配分三档**：有直接证据 / 可迁移 / 暂无证据。「可迁移」指有相关事实但没用 JD 的说法，给一版改写草稿，用户点采纳才进简历。缺口区也不列「你缺什么」，改成追问卡，回答完直接写回经历库，下次就能用。

**校验走两层。** 节点 6 让模型标风险，本地再跑一遍硬规则（强度词、虚构数字、项目名、标签状态），高风险拦住不让保存，中低风险只提示。校验不保证全对，最终还是人工审核为准。

匹配页是五列表：JD 能力要求、匹配经历、证据原文、状态、判断理由。每条证据必须命中已确认经历的原文连续子串，否则显示「无引用」；简历页的项目和标签同样要命中已确认经历，否则判高风险。

## 评测怎么做的

内置 8 组示例样本，注入三类已知缺陷（参与→主导、虚构 73%、未确认标签），这样漏检率可复现，不用等模型偶然犯错。样本是探索性的，不代表真实市场表现。

**第一轮 V1 vs V2。** V2 一口气改了 5 个节点，Precision 从 78.6% 升到 100%，但 Recall 从 61.1% 掉到 33.3%——它把原本有直接证据的「A/B 实验」「数据分析」这些降级成了暂无证据。回滚 V2，保留 V1。

**第二轮 V2a。** 只改节点 3 一条约束，其余回退 V1，同集跑两次。两次 F1 都高于 V1（85.7% / 80.0% vs 约 68.7%），方向一致，留作新候选。但没改动的节点指标也在波动（标签抽取 28.6% ↔ 42.9%，Precision 88.2% ↔ 100%），所以单次跑分只能看方向，不能当精确结论。

**V3 真实跑分**（6 节点 × 8 组，填 Key 跑完整链路）：

| 指标 | 结果 |
|---|---|
| 可迁移命中 | 100%（2/2） |
| 追问卡覆盖率 | 60%（6/10） |
| 匹配 Precision / Recall | 91.7% / 61.1% |
| 事实错误率 / 系统兜底后 | 0% / 0% |
| 模型误报率 | 9.1%（4/44） |

首版口径算出来是「可迁移 50%、误报 80%」，查 badcase 后发现是评测自己的问题：能力名多写「能力」两字就算不命中（事实片段其实完全相同）、误报率分母用了缺陷总数 25 而不是模型实际标注的 44 条、重复告警被算成误报。三处都改了，原始运行数据一个字节没动，重算结果作为 `reanalysis` 追加在同一份 JSON 里，可完整对照。改动理由写在 [DECISIONS.md](DECISIONS.md)。

还没解决的：追问卡覆盖率 60%、匹配 Recall 61.1%、可迁移冗余 5 项。采纳率需要真实用户点「采纳」才能测，这个 Demo 没有用户，标「待验证」。

## 边界

离线 Demo，没上线、没用户、没商业数据。不承诺过 ATS 或提高面试成功率。事实校验也不能保证零错误，最终内容以人工审核为准。API Key 只存本地，示例样本为脱敏数据。

- `core.js` — 六个节点的 prompt、schema、校验函数，两个页面共用一份，避免两处 prompt 漂移
- [PROMPTS.md](PROMPTS.md) — prompt 版本记录
- [DECISIONS.md](DECISIONS.md) — 关键决策与权衡
