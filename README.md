# AI 求职经历资产管理助手

> 针对求职者反复改简历却容易夸大经历的问题，设计了基于个人经历证据的固定 Workflow，通过评测集与 badcase 迭代，在降低事实错误的前提下生成岗位定向简历。

## 如何运行

直接用浏览器打开 `index.html`。首次使用请在页面右上角「设置」中填写 DeepSeek API Key（保存在本机浏览器 localStorage；解析时会随请求发送至 DeepSeek API）。

经历库：新增经历时先在弹窗顶部粘贴**经历原文**，点「AI 解析抽取」，节点 1 自动回填结构化字段并生成能力标签；每个标签附原文证据、默认「待确认」，逐条点「确认」后才进入正式资产，可修改（修改后回到待确认）或删除。无原文依据的标签会被本地校验直接丢弃。

JD 分析 Tab 支持粘贴并解析岗位描述、编辑结构化 JSON 画像、查看节点输入摘要 / 输出 / 耗时。JD 原文和解析结果保存在浏览器 localStorage。API Key 从「设置」读取；此单文件 Demo 会在浏览器中直接调用 DeepSeek 兼容接口。

匹配分析 Tab 只用「已确认」经历与标签，五列表格展示每条能力要求的证据与状态，缺口区给具体补充提问。简历生成 Tab 基于已确认经历 + 匹配结果生成定向简历；左侧简历字段可直接编辑，右侧是事实风险清单；存在高风险时「确认并保存版本」被阻断，改完点「重新校验（本地）」重跑强校验。

评测 Tab（工作台第 4 个入口也可进入）：选 Prompt V1 / V2 与样本数，点「运行评测」即对每组样本自动跑完 6 个节点；结果表列出指标、口径与分母，逐样本可展开完整节点输出。跑过 V1 和 V2 后自动出现同集对比表。可导入自己的 `samples.json` 替换内置样本，并导出含完整输出与两版 prompt 全文的 JSON。每次运行约 6 次模型调用/组，双版本全量约 96 次，建议先选「前 3 组」试跑。

## 核心设计

- **证据约束**：每条能力标签的 evidence 必须是原文连续片段（本地二次校验）；每条匹配结论必须引用经历原文，无引用判「暂无证据」，禁止仅凭关键词相似判定匹配。
- **匹配页五列数据来源**（作品集主图，固定表格不用卡片）：
  | 列 | 数据来源 |
  |---|---|
  | JD 能力要求 | `matchResults.matches[].ability`（源自节点 2 的 `core_requirements[].ability`） |
  | 匹配经历 | `matches[].experience`（模型输出的项目名，且必须命中已确认经历，否则本地降级） |
  | 证据原文 | `matches[].evidence`（必须是某条**已确认经历**原文的子串，否则显示「无引用」） |
  | 状态 | `matches[].match_status`（有直接证据 / 待确认 / 暂无证据，文字+色块双重区分） |
  | 判断理由 | `matches[].reasoning`（含本地降级标注） |
- **审阅闸门（Human-in-the-loop）**：标签「待确认/已确认」两态是核心设计——AI 只提出候选，人为真实性背书；它阻止幻觉流向后续简历生成、划清责任、让 badcase 可归因到具体节点。详见 [DECISIONS.md](DECISIONS.md)。
- **固定 Workflow 而非 Agent**：六个节点（经历结构化 → JD 解析 → 经历匹配 → 缺口识别 → 简历生成 → 事实校验）各有明确输入输出，可逐节点审阅与归因。选择理由见 [DECISIONS.md](DECISIONS.md)。
- **事实校验双闸**：节点 6 做模型标注 + 本地 `localFactCheck` 硬规则复查（职责强度词、虚构数字、项目名一致性、待确认标签），后者不信任模型自律、可在编辑后随时重跑；高风险阻断保存，中低风险只提示。校验不能保证绝对正确，必须保留人工审核。
- **简历页字段数据来源**：
  | 展示项 | 数据来源 |
  |---|---|
  | 个人概述 | `resumeVersions.summary`（节点 5 输出，仅用已确认信息） |
  | 项目条目 | `resumeVersions.projects[]`，顺序经 `sortProjectsByMatch` 按匹配状态本地重排 |
  | 项目名 | `projects[].project_name`，必须命中已确认经历，否则判高风险 |
  | 职责 / 行动 / 结果 | `projects[].responsibilities/actions/results`，对照经历原文校验强度词与数字 |
  | 能力标签 | `resumeVersions.skills[]`，必须是已确认标签，否则判「待确认写成事实」 |
  | 风险清单 | 节点 6 `risk_items`（source:模型）+ `localFactCheck`（source:本地）合并 |

## 评测

内置评测集 N=8（示例 / 脱敏数据），**探索性样本，不代表真实市场表现**。每组结构：`{id, jd, experiences, ground_truth:{abilities, correct_matches, skill_labels, fact_check}}`；可在评测 Tab 导入自己的 `samples.json` 替换。真实运行结果与完整节点输出见 `docs/eval/eval-run-2026-11-23.json`。

| 指标 | 口径（分母全部公开，micro 汇总） |
|---|---|
| JD 能力提取准确率 | 命中人工标注能力数 / 标注能力总数；多提的能力单列为「能力冗余」 |
| 能力标签抽取准确率 | 命中标注标签数 / 标注标签总数；evidence 非原文子串的标签在节点 1 后已被丢弃 |
| 经历匹配 Precision | TP / (TP+FP)，阳性 = 判为「有直接证据」；只看关键词相似不算命中 |
| 经历匹配 Recall | TP / (TP+FN)，分母 = 标注为有直接证据的项；防止全部判「暂无证据」刷高 Precision |
| 事实错误率（模型漏检） | 评测时向生成简历**注入 3 类已知缺陷**（参与→主导、虚构 73%、未确认标签），模型未检出数 / 注入缺陷总数 |
| 系统兜底后错误率 | 模型 + 本地强校验合并后仍未检出数 / 注入缺陷总数；与上一行对比即为护栏价值 |
| 模型误报率 | 模型标风险但不在注入缺陷集内的项 / 注入缺陷总数 |
| 人工修改率 / 用户采用率 | **待验证**——无真实用户与埋点，不填 0、不估算 |

注入缺陷是评测手段，不进入产品流程；用固定污点而非等模型偶然犯错，才能让漏检率可复现、可归因到节点 6。V2 是基于 badcase 的候选改动，是否保留以同集复测指标为准，见 [PROMPTS.md](PROMPTS.md)。

### 本次真实复测结果（2026-11-23，N=8，同集、同口径）

| 指标 | Prompt V1（基线） | Prompt V2（候选） | 结论 |
|---|---|---|---|
| JD 能力提取准确率 | 73.3%（22/30） | 73.3%（22/30） | 无变化 |
| 能力标签抽取准确率 | 38.1%（8/21） | 23.8%（5/21） | V2 变差 |
| 匹配 Precision | 78.6%（11/14） | 100%（6/6） | V2 变好 |
| 匹配 Recall | 61.1%（11/18） | 33.3%（6/18） | V2 明显变差 |
| 匹配 F1（衍生） | 约 68.7% | 约 50.0% | V1 整体更优 |
| 事实错误率（模型漏检） | 4%（1/25） | 4%（1/25） | 无变化 |
| 系统兜底后错误率 | 4%（1/25） | 4%（1/25） | 无变化，本地护栏有效 |
| 模型误报率 | 12%（3/25） | 8%（2/25） | V2 略好 |

**决策：回滚 V2，保留 V1。** V2 用大量漏匹配换 Precision：case-01 / 03 / 06 / 07 中原本有直接证据的「A/B 实验」「数据分析」「用户反馈分析」等被强度降级规则误降为暂无证据。由于 5 个节点同时改动，本次差异只能归因到 V2 配置整体；下一轮改为单点试验 V2a（只留反关键词约束、删掉强度降级规则）。这比"调了 prompt 效果更好"的叙事更真实，也更能说明评测的价值。

### 第二轮迭代：V2a（2026-11-25，闭环复现）

只改节点 3 一条约束、其余节点回退 V1，用同一 8 组样本跑了两次：

| 指标 | V1 基线 | V2a 第 1 次 | V2a 第 2 次 |
|---|---|---|---|
| JD 能力提取 | 73.3% | 83.3% | 83.3% |
| 能力标签抽取 | 38.1% | 28.6% | 42.9% |
| 匹配 Precision | 78.6% | 88.2% | 100% |
| 匹配 Recall | 61.1% | 83.3% | 66.7% |
| 匹配 F1 | ≈68.7% | ≈85.7% | 80.0% |
| 事实错误率 | 4% | 4% | 4% |

**决策：保留 V2a 作为新候选基线。** 两次 F1 都高于 V1，JD 提取两次都提升，方向一致。但没改动的节点指标也在波动（标签 28.6%↔42.9%、P 88.2%↔100%、R 83.3%↔66.7%），说明**模型调用有随机性，单次跑分只能看方向不能当精确结论**。原始输出见 `docs/eval/eval-run-2026-11-25-v2a.json` 和 `eval-run-2026-11-25-v2a-repeat.json`。

评测面板已支持 V1 / V2a / V2（存档）三个配置，对比表自动用「V1 vs 当前候选」。这就是完整的迭代闭环：找 badcase → 写假设 → 同集复测 → 看数字 → 保留或回滚 → 写进 PROMPTS.md → 下一轮。

## 边界声明

- 本项目为个人离线 Demo，**无真实用户、无上线数据、无商业转化**。
- 不承诺简历通过 ATS 或提高面试成功率。
- 事实校验不能保证 100% 无错误，最终内容以用户人工审核为准。
- API Key 仅存本地；评测样本为示例 / 脱敏数据，N=8，指标仅用于版本间相对比较，不代表真实市场表现。
- 人工修改率 / 用户采用率因无真实用户数据一律标注「待验证」，不填 0、不估算。
